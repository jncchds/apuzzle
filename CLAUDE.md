# APuzzle

A Flutter collection of grid logic puzzles, generated on the device. Package: `ua.pp.chds.apuzzle`.
Platforms: Android (the priority), Windows desktop (the main dev loop), web, iOS.

## Releases and release notes
Releases are `release/X.Y.Z` branches on the remote (pushing one runs `.github/workflows/release.yml`; the version comes from the branch name, not pubspec). `RELEASE_NOTES.md` has one `## X.Y.Z - YYYY-MM-DD` header per release, newest first, with short user-facing bullets; it is bundled as an asset and shown under Settings → Release notes (`/release-notes`). With every commit:
1. `git fetch`, then check whether the top version in `RELEASE_NOTES.md` exists as `origin/release/<version>`.
2. If it does, add a new version on top with the commit's notes: the next minor (X.Y+1.0) for a new puzzle or a major feature, the next patch for cosmetic changes and bug fixes.
3. If it doesn't, add the commit's notes to that top version. If that version is only a patch bump and the commit brings a new puzzle or a major feature, raise it to the next minor.
4. Either way, set the top version's date to today.

## Architecture
- `lib/core/puzzle_type.dart`: the `PuzzleType<P, S>` plug-in contract. P is the immutable puzzle (clues and solution), S is the immutable play state.
- `lib/core/value_grid.dart`:
  - `ValueGridType` is the base for "one value per cell" puzzles. It gives you:
    - the board, cycle/palette input, pencil marks and palette;
    - hints and state serialization.
    - slides: a drag starts as a tap on its first cell, and the cells it then crosses get the same change if they held what that cell held (the eraser clears anything); the whole slide is one undo step (`GameController.apply(merge: true)`);
    - `markForbidden` (optional): a long press dots every cell the placed objects rule out (Crowns, Campsite, Pairs, Fleet). Without it a long press is the same as a right click (`onCellSecondary`: cycle back / erase).
  - Subclasses supply `values`, rules (`isSolved`, `conflicts`), `generate`, and optionally `buildOverlay`, `cellColor`, `buildValue` and `buildEmpty` (content of an empty cell). Edge clues get bands: `header()` left/top, `footer()` right/bottom (`BoardMetrics.ox/oy` and `ex/ey`).
- `lib/core/latin_square.dart`: shared core for Latin-square games (the `latin` family: Skyline, Cages, Signs). `LatinSquare.of(n)`: candidate masks (bit d = digit d, solved = one bit), lines (rows 0..n-1, columns n..2n-1), traced `propagate` (placed digit ruled out in its lines, hidden singles, optional naked pairs), `remove` (an elimination by a type's rule, recording a follow-up naked single), `lineFills` (every way to fill one line that a predicate accepts, with prefix pruning), `countSolutions`/`probe` taking the type's propagate, and `random` Latin squares. Rule ids: `LatinRule` 0..`latinRuleCount`-1, a type's own rules from `latinRuleCount` up. `LatinExplainer` (a `MaskGridExplainer`) seeds candidates from the board and describes the Latin rules with shared `exLatin*` texts; a type adds `describeRule` and `placingTypeRules`.
- `lib/core/game_controller.dart`: the generic session. It handles:
  - undo/redo (full-state snapshots), timer, submit/hint;
  - saving and resuming (shared_preferences), and win detection and stats.
- `lib/core/generator_runner.dart`: runs `type.generate(params)` via `compute`, which is an isolate on native platforms.
- `lib/ui/board/cell_grid_board.dart`: a fit-to-screen grid with no zoom, and the win ripple. `cell_tile.dart` is the standard animated cell.
- `lib/ui/app_router.dart`: `MaterialApp.router`. The route is the URL: `/` (searching: `/?q=<text>`), `/c/<category>`, `/f/<family>` (over its category), `/settings`, or `/?p=<share code>` (a game opened while browsing keeps its page: `/c/grids?p=<code>`), so the web gets browser back/forward and Android share links use the same parser. The web build uses path URLs, and the Pages deploy copies `index.html` to `404.html`. Open screens through `AppRouterDelegate.of(context)`, not `Navigator.push` (dialogs and sheets are fine).
- `lib/core/registry.dart`: register new types here, in `puzzleTypes` and in one `PuzzleFamily` of one `PuzzleCategory` in `puzzleCategories` (numbers, grids, paths, casual; names are `cat*` ARB keys). A family of one has its game's id and opens the new-game sheet directly; a family of several variants (e.g. `flood`: Mosaic, Blend) gets a page (`FamilyScreen`) with a `fam<Id>` name and a `fam<Id>About` line on what they share.
- Home screen (`lib/ui/home_screen.dart`, `lib/ui/browse_screens.dart`): a search bar, "your games" (pinned first, then played last: `GameStore.pinnedGames`/`recentGames`, prefs `games.*`, kept on the device and not exported; `GameScreen` marks a game played, a long press on a game card or the pin on the new-game sheet pins it), the daily card, and one tile per category. A category page (`CategoryScreen`) shows family and game cards.
- Search (`lib/core/search.dart`): one list of games for any category. Every query word must start a word (case- and accent-insensitive, `searchWords`) of the game's name, tagline or tags (`gameTags`, translated `tag*` ARB keys that may list synonyms since they are never shown), in any of the four languages. Games found only by another name (`gameAliases`: Nurikabe, Slitherlink, Queens…) are listed under "We don't have “<query>”, but you might like:" (the player's text, never the alias). When nothing matches, names and other names are tried with typos allowed (one edit for 4–6 letters, two from 7: "Did you mean:"), and failing that the closest games (`_closest`: up to 5 with the fewest edits from each query word to any part of a word, names first), so a query with any letters or digits always finds something; the category tiles only show for a query with none. Aliases are for matching only: never show them in the UI, store listings or app metadata.
- Daily challenges (`lib/core/daily.dart`, `lib/ui/daily_screen.dart`, route `/daily?d=2026-09-25[&p=<code>]`):
  - each day picks 3 games (seeded by `hash31(date)`, a web-safe FNV-1a) from the types whose `dailySince` is on or before it (launch: 2026-09-01), each at its `dailyDifficulties` (all by default; 2048 only medium);
  - the player can leave games out (the tune button on the daily screen, at least 3 stay): `dailyChoices` is a history of `(from, excluded ids)` kept by `GameStore` in `dailyPool`, and a change counts from today, so earlier days keep their games. Excluded ids are stored (not chosen ones), so a new puzzle joins everyone's selection by default. The exception is a type with `dailyOptIn` (the memory games, and any later casual game; Snake and older ones predate it): `choiceExcluded` adds it to every choice made before its `dailySince`, so it starts left out for players who already had a selection while players without one get it; once it is out, the tune sheet shows it unchecked, and saving makes that explicit. It travels with the progress export, but a device that has its own history keeps it;
  - every puzzle of the day uses the same seed, with the type's fixed `dailySize(difficulty)` and default options, so it is a normal share code;
  - `GameStore`: results in `daily.<date>` (`type.difficulty` → code, best ms, hints), in-progress dailies in their own save slot (`save.daily.<code>`), so they never replace the free game. Daily wins also count in the regular stats;
  - the router only treats a code as a daily one if it really is that day's puzzle (`isDailyPuzzle`), and never for future days.
  - a free game that wins with a daily puzzle's code (a shared link, or by chance) is recorded for that day too (`dailyDayOf`, in `GameController._win`).
- Moving progress between devices (`lib/core/backup.dart`, `lib/ui/transfer_tiles.dart`, Settings): `exportProgress` packs the `stats.`/`daily.`/`save.`/`tutorial.`/`strategies.`/`last.` prefs (settings stay on the device), and `ProgressCode` turns them into `APUZZLE1:` text scrambled with a fixed key that's committed here. It isn't a secret, just a speed bump against editing times. The same text goes to a file (`file_picker`) or the clipboard. `importProgress` merges and never replaces:
  - stats keep per-device win counts (`PuzzleStats.devices`, keyed by the random `device.id`) and take the larger count per device, so repeated imports and round trips never count a win twice;
  - best time/score and per-puzzle daily times take the better value, and `done`/`true` beats `skipped` for tutorial and strategy marks;
  - saves carry an `at` stamp (`writeSave`), and the newer one wins. A daily save is dropped if that puzzle is already solved here. Last choices stay local.
- `lib/core/grid_graph.dart`: neighbour lists and connected components for flat grids.
- Tutorials (`lib/core/tutorial.dart`, `lib/ui/tutorial_screen.dart`, `lib/ui/learn_screen.dart`, routes `/learn`, `/learn?t=<id>` and `/learn?t=<id>&s=1`):
  - each type's `tutorial()` returns `TutorialStep`s from `lib/puzzles/<id>/<id>_tutorial.dart`: a tiny hand-made board (or `TutorialStep.generated` for the final "real board"), a text (`tut<Type><n>` ARB keys), cells to point at, and either "solve it" or a custom `done` goal with an `answer` state;
  - steps run on the real board in a `GameController(practice: true)` (no saves, no stats); "Show me" is the type's hint (or the step's `answer`);
  - the first new game of a type (new-game sheet, daily screen) calls `offerTutorial`: "No, thanks" (or leaving the tutorial halfway) marks it offered, finishing marks it done (`GameStore.setTutorial`, `tutorial.<id>`); players with stats or a save are never asked;
  - strategies: each type's `strategies()` (same file, `tut<Type>S<n>` keys) are optional advanced lessons, one technique per board, usually ending with a generated hard board. The learn screen has Basics/Strategies tabs, the basics' last page offers "Learn strategies", and finishing them sets `strategies.<id>` (they never count as "offered"). A strategy board should need its technique: check it with the type's solver (the tier below gets stuck, the taught tier solves it) and pin a generator seed that does;
  - `test/core/tutorial_test.dart` checks every step of both lists: solvable by "Show me", not solved at the start, and exactly one solution for value-grid boards (unless `openEnded`).
  - Tutorial texts never name colors ("white cells", "gray clue") since the themes differ; say "empty cells", "clue cells", "walls" instead.
- Explain mode (`lib/core/explain.dart`, `value_grid_explain.dart`, `loop_explain.dart`, `lib/ui/explain_panel.dart`, `lib/ui/board/explain_overlay.dart`):
  - solvers take an optional `ExplainTrace` and record every deduction as `trace?.fact(slot, value, rule, premises:, args:)` (and `trace?.fail(...)` at each contradiction); null-aware calls cost nothing when off. Each type has a rule enum (`MamboRule`, `SudokuRule`, …). `LoopSolver` subclasses call the cheap `because(rule, arg)` before `set` instead (rules from `loopRuleCount`), and a clashing `set` records why;
  - `<id>_explain.dart` is the type's `Explainer`: seed knowledge from the board (only entries that agree with the solution), run the solver's levels, probe, say which facts the board can show (`move`), and turn facts into texts (`describe`). Hooks: `rank` (show crowns before the dots they imply), `quiet` (facts that go without saying in a chain), `start` (facts known from the start, like one-cell regions), `optionalValues` (notes like dots or grass the board needn't have). Bases: `ValueGridExplainer`, `BinaryGridExplainer`, `MaskGridExplainer`, `LoopMarksExplainer`, `LoopRuleTexts`;
  - `explainStep` fixes a wrong entry first, then picks the shown fact with the best rank and the shortest chain of reasons; a probing level tries assumptions whose refutation the board can show first, else refutes every hidden one it finds in one pass; a stall falls back to revealing a cell. Path types (Trail, Links) only show steps that extend a drawn path from its end;
  - types opt in with `canExplain` and `explain()`; `GameController` toggles the mode (entering = 1 hint, each applied step = 1 hint), keeps `explanation` in step with the board, and `hint()` plays the explained step;
  - an `ExplainLine` with a `key` is told once per story (one naked pair ruling out several cells);
  - texts are `ex<Type><Rule>` ARB keys (shared `exLoop*` for loops) whose placeholders get tokens: `cellTok` → "E4", `rowTok`, `colTok`, `areaTok`, `cellsTok`, `sideTok` (a cell side, drawn with an arrow), `linkTok` ("C3–C4"), `valTok` (the board's own symbol via `buildValueChip`); never name colors. Counts use ICU plurals. While on, boards show A1-style coordinates and highlights (`ExplainView`, `CellGridBoard.explain`, `LoopBoard.explain`);
  - `test/core/explain/` (`explain_checks.dart`, split by type into `explain_<k>_test.dart` shards so they run in parallel) solves boards of every size and difficulty (4 seeds at the default size, 1 elsewhere) step by step with no fallback, checks the texts in all four languages, the wrong-entry fix, and the tutorial and strategy boards;
  - not offered for Mosaic, Blend, Pop, 2048, Homeward, Blockade (optimization, no deductions), Pipes (any tree wins), Channel (any route wins), Inlay (any cover wins), Labyrinth (exploration) and Formula (guessing).
- Localization: gen-l10n (`l10n.yaml`), ARB files in `lib/l10n/` (en is the template; uk, pl, de). Generated `app_localizations*.dart` are checked in; run `flutter gen-l10n` after editing ARBs. No user-facing string literals in Dart: use `context.l10n` (`lib/l10n/l10n.dart`). Type texts take an `AppLocalizations` (`name(l)`, `tagline(l)`, `rulesText(l)`, `finishTitle(l, …)`); toasts and puzzle-code errors carry a `Tr` closure resolved by the UI. Language: `Settings.language` (null = system); `resolveAppLocale` maps Russian to Ukrainian and anything unsupported to English.
- Memory games (`lib/core/recall.dart`, `lib/ui/board/recall_board.dart`): `RecallType` is the base of the casual memory games. A round is a `List<int>` the type reads, drawn from (seed, round number, level) by `makeRound` (`recallRound`, cached; `RecallPuzzle.fixed` rounds come first, for tutorials), so share codes replay. Phases in `RecallState`: show (`showMs`, Ready hides it early; or until the first tap with `answerWhileShown`) → answer (taps checked by `accepts`/`verdict`) → result → next round or done. Right = +level score and one level up, a miss = one level down (`levels(size)`, `startLevel`; difficulty also sets `pace`, the show time in percent). `recallHide`/`recallTap`/`recallNext` are pure; `recallAuto` plays the right move (`hint`, for tests and snapshots only: `realTime`, so no undo, redo or hints in play). Goal option: 10 rounds or 3 lives; always `isSolved` at the end (a score game). `RecallBoard` times the phases with one `AnimationController`, and waits for a tap on a new game and after the app was in the background (so a round never runs out unseen); `RecallControls` shows round or lives, score, and the status line or Ready. Tutorials use `recallPractice`: fixed rounds, a miss replays the round, done after N right ones.
- Game options: a type can declare extra new-game choices with `optionsFor(chosen)` (later options may depend on earlier ones). They live in `GenParams.options`, go into share codes after the difficulty (`pop-10x8-hard.std.clear-SEED-v1`), and stats are kept per `GenParams.variant`. Option and choice texts come from `optionLabel`/`choiceLabel`/`choiceDescription`. Score games override `score()` (best score in stats) and `finishTitle()`.

## Adding a puzzle type
1. Create `lib/puzzles/<id>/`, containing:
   - `<id>_model.dart`: the puzzle plus a pure rule check;
   - `<id>_solver.dart`: tiered, sound deductions plus `countSolutions(limit: 2)`;
   - `<id>_generator.dart`: random solution → strip clues while still solvable at the difficulty's tier;
   - `<id>_type.dart`, including `dailySize` (must fit a 360×760 phone) and `dailySince` set to the day after the push to origin (the release date + 1), so earlier days, the release day included, keep their games. If the push slips to a later day, move `dailySince` and the release note along;
   - `<id>_tutorial.dart`: 3–5 tiny boards, one rule or edge case each, ending with a small generated board; override `tutorial()` in the type. Add 1–3 strategy lessons too (`strategies()`);
   - `<id>_explain.dart`: trace the solver's rules and add an `Explainer` (see Explain mode), with `ex<Id>*` texts;
   - `<id>Name`, `<id>Tagline`, `<id>Rules`, `tut<Id><n>`, `tut<Id>S<n>` (and any other texts) in all four ARB files.
2. Generation must be deterministic for a given `GenParams.seed`, and pure, because it runs in an isolate. Types must be `const`.
3. Add it to `puzzleTypes` and to one family (its own, or a family of variants) of one category in `puzzleCategories` (`registry.dart`). Give it search tags in `gameTags` (add a `GameTag` with `tag*` texts in all four languages if none fits) and the other names it is known by (original or trademarked names) in `gameAliases` (`search.dart`).
4. Add tests in `test/puzzles/<id>/`. Across seeds, sizes and difficulties, check that:
   - the solution is valid;
   - the puzzle has exactly one solution;
   - it is solvable at its tier;
   - generation is deterministic and fast.

## UX rules (from the user)
- No live error highlighting by default (a setting turns it on). Validation happens on Submit, and the game auto-wins when it's complete and correct.
- No zoom. Sizes are capped by `fittingSizes()` (a 36px minimum cell).
- Grid size is variable in every game. Input supports both tap-to-cycle and palette stamping, with pencil marks where useful. Pencil marks are kept under a value: removing the value (tap it again, eraser, cycling to empty) shows them again; the eraser on an empty cell clears the marks.
- Region outlines (`RegionBorders`) have rounded corners: a lone bend is an arc, and where three or four lines meet the inner corners are filled in.
- Shikaku draws a rectangle faint while it can't stay as it is (no number, several, or the wrong area).
- Use our own puzzle names and art, not LinkedIn's or the source app's (Tango, Queens, Zip, Mambo, Kings, …).
- Original or trademarked puzzle names (Nurikabe, Slitherlink, Queens, …) appear only in code and developer notes (`gameAliases`, this file). Never in anything players or stores see: ARB texts, README, PUZZLES.md, RELEASE_NOTES.md, web/app metadata. Keep them out of commit messages too, since the history is public.
